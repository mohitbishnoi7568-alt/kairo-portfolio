On building small tools

Nov 18, 2026 · 4 min read · Kairo

Most of the software I'm proud of started as something I needed for myself: a script to rename a folder of photos, a page that turned a messy list into a clean one, a tiny command that answered a question I asked every week.

That origin matters. When the problem is yours, you know when the tool is done — the moment it stops being annoying. The sections below are a short version of the process I keep coming back to.

Start smaller than feels useful

The first version should solve exactly one case. It is tempting to add flags, configuration and a plugin system immediately. Resist that for a while. A tool with one job is easy to understand and easy to throw away, and both of those are useful properties.

A small tool you understand completely beats a large tool you only half trust.

Make the result visible

Good tools show their work. If something takes a few seconds, say so. If a file changed, name it. If nothing happened, say that too. It is less about polished output and more about trust.

Write it down before you forget

After the tool works, spend five minutes on the README. Not a manual — just the command that starts it, one example, and the thing it deliberately does not do.

  • One sentence on what it is.
  • One command that runs it.
  • One example of real output.
  • One known limitation.

Wrap up

Build the smallest thing that removes a real annoyance, make its behaviour obvious, and leave a note for later. That is the whole method.
