Notes on testing

Aug 21, 2026 · 6 min read · Kairo

I do not aim for a perfect test suite. I aim for a small set of tests that catch the mistakes I actually make. Everything else is a nice idea that has to earn its place.

What stays

Boundary cases, parsing of untrusted input, and any bug that has happened twice. Those tests are cheap to write and painful to live without. A regression test is a promise to your future self that you will not re-solve the same problem.

// good: a bug that already happened once
it('rejects an empty email', () => {
  expect(validate('')).toBe(false);
});

What goes

Tests that only repeat the implementation, that assert a framework detail, or that need three mocks before they say anything. If a test breaks whenever the code is tidied, it is measuring the wrong thing.

A test should describe a behaviour, not a line of code.

The loop

See it fail, make it pass, then tidy. The middle step is the tempting one to skip, but watching a test fail is how you learn that it was testing what you thought. Keep the loop small enough that it fits in one sitting.

  • Write one example of the behaviour you want.
  • Run it and watch it fail for the right reason.
  • Make the smallest change that passes.
  • Delete anything the test no longer needs.

Wrap up

Fewer, sharper tests. The goal is not a number in a report — it is the confidence to change something on a Friday afternoon.
